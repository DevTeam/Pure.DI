#### Roots in other namespaces

`Roots<T>` discovers implementations that are visible from the setup location, so an implementation declared in a namespace that is not imported is invisible and the compilation fails with `DIE016`.
Passing `searchInCompilation: true` searches every type declared in the current assembly instead, so `EmailService` is found even though nothing imports `Impl`.
The full search is opt-in because it walks the whole assembly; the default lookup from the setup location stays the fast path.


```c#
using Shouldly;
using Pure.DI;

DI.Setup(nameof(Composition))
    .Roots<INotificationService>("My{type}", searchInCompilation: true);

var composition = new Composition();
composition.MyEmailService.ShouldBeOfType<Impl.EmailService>();

public interface INotificationService;

namespace Impl
{
    public class EmailService : INotificationService;
}
```

Prefer a `using` directive when the namespace is known: it keeps the generated set explicit and costs nothing at generation time.
Reach for `searchInCompilation: true` when the setup lives in its own namespace and plugin implementations are spread across the assembly.
The option is available on `Builders<T>` as well and combines with `filter`.
When no type matches at all, the message names the implementations that exist in the compilation but are not visible and suggests the fix.
